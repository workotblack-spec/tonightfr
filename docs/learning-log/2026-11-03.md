## Leçons à retenir

- GitHub est le classeur du code ; la base est le carnet vivant des réservations. Sauvegarder le classeur ne sauvegarde pas le carnet.
- Une migration est une consigne de transformation ; son fichier n’est pas la preuve qu’elle a été appliquée à cette base.
- RLS est la porte d’accès ; il faut encore vérifier à qui les clés ouvrent réellement.
- Un compte propriétaire unique n’est pas encore une équipe gérant plusieurs établissements.
- Un site visible n’est pas une application validée en production.
- Une information contradictoire doit rester visible comme un écart à résoudre, pas être présentée comme certaine.
- Un secret se traite dans les réglages sécurisés, jamais dans le journal pédagogique.

**Actions réelles :** SELECT sur `supabase_migrations.schema_migrations` et `drizzle.__drizzle_migrations` ; empreintes MD5 (Supabase) et SHA-256 (Drizzle) calculées côté fichiers et côté base, puis comparées. Aucun contenu de migration affiché ; seuls les chemins des fichiers à motif sensible ont été notés.

**Résultats :** 17 fichiers Supabase ↔ 17 lignes (14 identiques, 3 écarts de quelques octets) ; 3 fichiers Drizzle ↔ 3 lignes identiques. Aucune migration en attente, aucun doublon. Voir [décision 0001](../decisions/0001-source-of-truth-migrations.md).

**Leçon — plan contre preuve :** un fichier de migration est comme une **recette** posée sur le plan de travail : il dit ce qu’on *compte* faire. Le journal `schema_migrations` est le **ticket de caisse** : il prouve ce qui a *réellement* été exécuté, et quand. Une recette peut avoir été raturée après coup (nos 3 écarts) ; le ticket, lui, garde la version cuisinée. Comparer les deux avant d’ajouter une migration évite de recuire un plat déjà servi (rejouer un changement) ou d’oublier un ingrédient (supposer qu’un changement est en place alors qu’il ne l’est pas).
